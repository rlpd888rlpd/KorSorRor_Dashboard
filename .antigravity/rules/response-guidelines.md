# Response Guidelines & Token Efficiency

เอกสารนี้กำหนดแนวทางการตอบคำถาม การอธิบาย และการส่งมอบโค้ดของ Agent เพื่อรักษาขีดความสามารถของ Context Window และประหยัด Token สูงสุด

---

## 1. No Full-File Rewrites (ห้ามส่งโค้ดทั้งไฟล์ซ้ำ)
- **กฎเหล็กเรื่อง Diff:** เมื่อต้องการปรับปรุงหรือแก้ไขโค้ดที่มีอยู่ **ห้ามส่งโค้ดกลับมาทั้งไฟล์เด็ดขาด**
- **รูปแบบการนำเสนอโค้ด:**
  - ระบุ **Path ของไฟล์** ชัดเจน (เช่น `src/features/dashboard/components/metric-card.tsx`)
  - ระบุ **ตำแหน่งหรือฟังก์ชันเป้าหมาย** (เช่น ฟังก์ชัน `calculateTotal()`, หรือบรรทัดที่เกี่ยวข้อง)
  - แสดงเฉพาะ **Diff Block (`+` / `-`)** หรือ Code Snippet สั้นๆ เฉพาะส่วนที่มีการเปลี่ยนแปลง
  - ใช้ Comment เช่น `// ... existing code ...` เพื่อแทนที่โค้ดส่วนเดิมที่ไม่มีการเปลี่ยนแปลง

---

## 2. Think Before Code & No Blind Assumptions
- **ถามเพื่อความกระจ่างก่อนเริ่ม:**
  - หากโจทย์, Logic ทางธุรกิจ หรือ Data Flow มีความซับซ้อนหรือไม่ชัดเจน **ห้ามเดาหรือสมมุติเอาเอง (No Blind Assumptions)**
  - ให้ถามคำถามที่ตรงประเด็นเพื่อยืนยันความต้องการทันที
- **สรุป Plan 2–3 บรรทัด:**
  - ก่อนเริ่มเขียนโค้ด ให้สรุปแนวทางเชิงสถาปัตยกรรมหรือ Action Plan สั้นๆ 2–3 บรรทัดให้ผู้ใช้เห็นภาพรวม
  - เมื่อได้รับความเห็นชอบ จึงเริ่มลงมือเขียนโค้ดหรือแก้ไขไฟล์

---

## 3. Concise Explanations & Direct Communication
- **ตัดคำเกริ่นที่ไม่จำเป็น:**
  - เข้าประเด็นทันที ไม่ต้องมีคำขึ้นต้นเยิ่นเย้อ (เช่น "แน่นอนครับ ต่อไปนี้คือแนวทางการแก้ไข...")
  - อธิบายเหตุผลเชิงเทคนิคและสถาปัตยกรรมอย่างกระชับ (Bullet points)
- **เน้น Logical Step-by-Step Delivery:**
  - ส่งมอบงานเป็นขั้นเป็นตอน: Flow & Schema -> Service/Hook -> UI Component
  - อธิบายว่าแก้ไขแต่ละส่วนเพราะอะไร และกระทบกับจุดใดบ้าง

---

## 4. Verification Steps (ขั้นตอนการทดสอบและยืนยันผล)
- ทุกครั้งที่มีการส่งมอบหรือแก้ไขโค้ด จะต้องมีหัวข้อ **Verification Steps** ประกอบด้วย:
  1. คำสั่ง Terminal สำหรับทดสอบ (เช่น `npm run build`, `npm run test`, หรือ `npx tsc --noEmit`)
  2. สิ่งที่ผู้ใช้ต้องตรวจสอบบนหน้าจอ Browser หรือ Supabase Dashboard (Expected Result)
  3. Edge cases หรือจุดสังเกตที่ควรระวัง
